Review the change, not the diff.

A review companion for GitHub pull requests and GitLab merge requests. It shows each changed function whole, where the rest of the code uses it, and what looks risky, then walks you through the parts that matter. It runs on your machine.

A diff shows which lines moved. A review needs more.

What changed in meaning, who depends on it, and where to look first. Walkdiff does that legwork, so your attention goes to judgement.

Reviewing a line diff

  • Hunks cut functions in half, with three lines of context.
  • A renamed or moved function looks like deleted code plus new code.
  • Formatting and comment edits look as important as logic changes.
  • Nothing says which callers the change affects, or which the PR left alone.
  • Files come in alphabetical order, whatever depends on what.

Reviewing with Walkdiff

  • Each changed function, method or type appears once, whole, before and after.
  • Renames, moves and formatting-only edits are recognised and folded away.
  • Each change lists its facts: parameters, return type, calls and error paths.
  • Every changed unit shows where the rest of the code still uses it.
  • A review path puts the riskiest changes first, one stop at a time.

What we believe

  1. 01

    Units, not hunks

    Code is reviewed as functions, methods and types, read from the syntax tree, so a change is seen the way its author thought about it.

  2. 02

    A path through the change

    A brief and a review path put the riskiest changes first, and say why each stop is there.

  3. 03

    Findings, not a grade

    It reports what it found and which checks ran or didn't. It never scores or approves a PR for you, and its rules would rather stay quiet than raise a false alarm.

  4. 04

    Your code stays yours

    Analysis runs locally. Code leaves your machine only for the host you review on, and for an AI model if you ask for one. Every other network use is listed, and --offline turns it off.

  5. 05

    AI that shows its work

    AI review is opt-in. Every statement must cite lines of the change, and citations that don't match what the model was shown are discarded.

  6. 06

    Fits how teams work

    The command line, a local app that tracks several reviews, or CI. Comments and approvals post back to GitHub and GitLab.

How a review goes

From a link to a posted review, without leaving the report.

Open a real report: Walkdiff reviewing one of its own pull requests.

  1. 1

    Point it at a PR or MR. It fetches only the merge base and head commits, and parses both versions of each changed file.

  2. 2

    Read the brief. What to check, how many changes need attention, and where to start.

  3. 3

    Walk the review path. One change per stop, with its code, callers, tests and findings, and why it's on the path.

  4. 4

    Post your review. Comments on exact lines and your decision go back to the PR from the app, or CI leaves a summary with a link to the report.

Where it's going

Walkdiff is an early release. The aim is a review companion that understands a change as well as its author does, in every language a team uses, and stays honest about what it couldn't check.

Deeper language support

Breaking-change detection for Java, C and C++, alongside Rust, TypeScript, Python and Go.

Reviewing stacks

Stacked PRs reviewed together, bottom first, with each PR's progress and what its host says now. It works today and keeps improving.

Fewer blind spots

Every check that can't run says so in the report. Each release turns more of those "not checked" lines into checks.
