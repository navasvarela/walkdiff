Manual

Everything Walkdiff does, briefly. The guides on GitHub have the details.

Your first report

You need Node.js 22.18 or newer, and git. Run Walkdiff with npx, or install it once:

npm install --global walkdiff
walkdiff review https://github.com/owner/repo/pull/123

Walkdiff fetches the change, analyzes it, and prints a local address to open. GitLab works the same way with a merge request link. GitHub Enterprise and self-managed GitLab work by URL too.

The first review also installs the security scanners Walkdiff runs, at pinned versions checked against their hashes. walkdiff setup installs them in advance.

OptionDoes
--out <dir>Writes the report to a folder instead of the cache
--no-serveWrites the report and exits. The HTML file also opens straight from disk
--offlineSkips everything that uses the network besides the host: vulnerability lookups, registry checks and Semgrep's rule download
--aiAdds an AI review
--coverage <file>Shows which changed lines ran in tests, from an LCOV or Cobertura report

Reading a report

The report opens on a brief: what to check, how many changes need attention, and where to start.

  1. Start the review. The review path takes you through the changes that matter most, one at a time, and says why each one is there.
  2. Mark what you've reviewed and leave comments as you go: on a whole change, or on exact lines by clicking a line number. Shift-click picks several lines.
  3. Finish. The last screen shows what you reviewed, what's left, and what Walkdiff couldn't check. In the app you can post your review from here.

Everything else is under All changes, in tabs you can link to, as in #risks:

TabShows
ChangesThe files, a map of each file, and every changed unit, whole, before and after
ImpactWhere other code uses what changed, and which of those callers the PR didn't touch
RisksEach finding, a summary of security findings, and the checks that ran and that didn't
AI reviewA reading order, an intent check and questions, when you ask for them
ConversationThe PR's threads, in the app, where you can reply and resolve them

"No security findings" means the checks that ran found nothing on the lines the PR adds. It isn't a security audit, so check which checks ran.

Changed units

In Rust, TypeScript, JavaScript, Python, Go, Java, Kotlin, C#, C and C++, Walkdiff parses both versions of each file and compares them unit by unit: functions, methods, classes, types and macros.

  • Whole, before and after. Each changed unit appears once, with edited words marked. A class shows only its own code, and its methods get their own cards.
  • Change facts. Each modified function lists parameters added, removed or changed, a new return type, calls added or removed, and more or fewer error paths and branches.
  • Noise folded away. Formatting-only and comment-only edits, renames with unchanged bodies, and moves between files or classes are collapsed. A function moved and edited shows as one "moved and edited" change. Lockfiles and generated files are grouped as skippable.
  • Tests as units. Each JavaScript and TypeScript describe, it/test and hook is named by its title, as parser › reads includes, and so is each GoogleTest or Boost.Test case in C++.
  • A map of each file. When a file has several changed units, an outline shows which ones changed among its definitions, their size, and which changed function calls which.

Other languages get a line diff, which is also there on demand for every file.

Impact

For every function, method or type a PR changes, removes or renames, Walkdiff lists where the rest of the repository still uses it, linked to the host, and flags the callers the PR didn't touch. A removed or renamed unit shows the references left behind.

References are found by name and syntax, not by type checking, so each carries a confidence:

  • Exact: qualified with the unit's type, as Size::new or this.parse().
  • Likely: a direct use of the name, as parse(x).
  • Possible: a method called on a value of unknown type, as x.parse().

Parameters and locals that shadow the name are ignored. A name used in more than 200 files is reported as too common to trace.

Risks and security

Built-in rules read the lines a PR adds, and only code counts, not comments or strings:

  • Secrets, redacted in the report.
  • Attack surface: new HTTP endpoints, a new one without the auth the other routes in its file declare, and code that turns auth or CSRF checks off, such as [AllowAnonymous] or @csrf_exempt.
  • Risky APIs, such as eval, shell=True, raw HTML, unsafe, disabled TLS checks, SQL built from strings, Java deserialization, or C's strcpy.
  • Sensitive areas: auth, payments, migrations, CI, and paths your team marks.
  • CI pipelines: injection through PR titles and branch names, unpinned includes and images in GitLab CI.
  • Review signals: large PRs, code changes without test changes, and removed units that untouched code still uses.

Pinned security scanners add more when they're installed:

ScannerFinds
SemgrepRisky code patterns, with the p/default rules
gitleaksSecrets
RuffInsecure Python, with Bandit's rules
osv-scannerKnown vulnerabilities in pnpm-lock.yaml, yarn.lock and bun.lock
zizmorSecurity problems in GitHub Actions workflows
poutineSecurity problems in GitLab CI, Azure Pipelines and Tekton

A PR can't silence a scanner: suppression comments such as # nosemgrep are ignored, and scanner config files in the PR aren't used. A scanner that can't run is listed under "Not checked".

Dependencies

When a PR changes package.json, Cargo.toml, pyproject.toml, requirements files, go.mod, pom.xml, Gradle build files and version catalogs, or their lockfiles:

  • New dependencies are noted where they're declared.
  • Known vulnerabilities in versions new to a lockfile are looked up in OSV.
  • Trust: a new direct dependency is flagged if it's known malicious, isn't on its registry, was first published in the last 30 days, or is one character away from a popular package's name.
  • Licences: list the licences your team accepts, and anything else is flagged.

Breaking changes

Walkdiff flags changes that could break other code or a deployment, and puts them on the review path:

  • Public APIs in Rust, TypeScript, JavaScript, Python and Go libraries: removed or renamed functions and types, lost visibility, new required or removed parameters, and changed types. Only code other projects can reach counts, such as a crate's public modules or a package's entry point.
  • Database migrations that drop or rename tables and columns, or change column types, in SQL and the common migration frameworks.
  • Configuration: renamed or removed environment variables and config keys that code still reads.

These rules read syntax rather than types, so they say "may break" and would rather stay quiet than raise a false alarm.

Code quality

A function is flagged when a PR adds it over a limit, pushes it over one, or makes one that's over a limit at least 20% worse. Test code is left out.

MetricLimit
Complexity (decision points)15
Nesting depth4
Lines80
Parameters6

Ruff, oxlint and jscpd add likely bugs in Python and JavaScript, and new code copied from elsewhere. Turn these checks off for a repository with { "quality": { "enabled": false } } in .walkdiff.json.

Test coverage

With a coverage report for the PR's latest commit, in LCOV or Cobertura format, each change shows whether its lines ran in tests, and changes that didn't run rank higher on the review path. Walkdiff finds reports in CI artifacts, in files the PR adds, or one you attach in the app or pass with --coverage.

AI review

With --ai, or the app's AI option, Walkdiff asks a model for:

  • a suggested reading order that groups the changes into chapters,
  • a check of the PR description against the code: matches, contradicts, not described, or not found,
  • specific questions to answer before approving.

Every statement must cite lines of the change, and citations that don't match what the model was shown are discarded. Claude is the default. Any OpenAI-compatible service works too, and so does a local model such as Ollama, in which case nothing leaves your machine. A repository can forbid AI review in .walkdiff.json.

The app

walkdiff app

A local page at http://127.0.0.1:4317/ that keeps track of several reviews.

  • A review list. Paste PR or MR links. Each one shows its status, counts and your progress, and says when the code changed since you reviewed it.
  • Post your review. The finish screen posts your comments and your decision to the host: Comment, Approve or Request changes. Nothing is posted until you press the button.
  • Conversation. Read the PR's threads beside the code, reply and resolve them.
  • Stacks. Add one PR from a stack and the app offers the rest. A stack is one card, bottom first, with each PR's progress and what the host says now. Refresh changed re-runs only the PRs that changed, and Approve all… approves the stack bottom first.
  • Settings turn optional checks on or off, choose the AI provider, and show what leaves your machine.

The server listens only on your machine, and its API needs a key created each run.

Private repositories

Set a token that can read the repository. With the GitHub CLI:

GH_TOKEN=$(gh auth token) walkdiff review https://github.com/owner/repo/pull/123

For GitLab, use a token with the read_api and read_repository scopes (api to post reviews):

GITLAB_TOKEN=<token> walkdiff review https://gitlab.com/group/project/-/merge_requests/45

Tokens stay out of the command line and the cached repository's config. Self-hosted instances receive a token only once you list them as trusted.

In CI

Each PR gets one comment, updated on every push, with a summary, the top findings linked into the diff, and a link to the report, kept as a job artifact.

GitHub Actions

name: Walkdiff
on: pull_request
permissions:
  contents: read
  pull-requests: write
jobs:
  report:
    runs-on: ubuntu-latest
    continue-on-error: true
    steps:
      - uses: navasvarela/walkdiff@v0.11.0

GitLab CI

include:
  - remote: https://raw.githubusercontent.com/navasvarela/walkdiff/v0.11.0/ci/gitlab-ci.yml

Set GITLAB_TOKEN as a masked, unprotected CI/CD variable with the api scope. The pilot guide covers coverage, AI review and running a trial with your team.

Team rules

A .walkdiff.json at the repository root sets rules for everyone. Every setting is optional:

{
  "riskPaths": [{ "pattern": "src/ledger/**", "severity": "high", "reason": "Moves customer funds" }],
  "ignore": ["tests/fixtures/**"],
  "ai": { "allowed": true },
  "dependencies": { "private": ["@acme/*"], "allowedLicenses": ["MIT", "Apache-2.0"] }
}

A PR can't change its own rules: Walkdiff reads this file from the PR's merge base, and reports an edit to it as a finding. The configuration guide lists every setting.
